# Packaging

Everything that turns the two launchers into something a user can install
lives in this directory. The version is never written out by hand: the
workspace version from `[workspace.package]` in the root `Cargo.toml` reaches
every template as `-DHylMailVersion=<version>` (Inno, WiX) or by replacing
`{{VERSION}}` (macOS), and `.github/workflows/release.yml` refuses a tag whose
name does not match that version.

| Target | Source | Built with |
|---|---|---|
| Windows, per user | `windows/hylmail.iss` | Inno Setup 6.7 (`ISCC.exe`) |
| Windows, per machine | `windows/hylmail.wxs` | WiX 3.14 (`candle.exe`, `light.exe`) |
| macOS | `macos/make-app.sh`, `macos/make-dmg.sh`, `macos/Info.plist` | `sh`, `lipo`, `hdiutil` |
| Linux, `.deb` | `[package.metadata.deb]` in `crates/hylmail-cli/Cargo.toml` | `cargo deb -p hylmail-cli` |
| Linux, tarball | `linux/make-tarball.sh`, `linux/de.hylmail.HylMail.desktop` | `sh`, `tar` |
| All | `icons/` | `cargo test -p hylmail-core --test icon_assets -- --ignored` |

The two Windows installers install the same two executables and both claim the
`HylMail.eml` file association, so **only one of them should be installed at a
time**. The Inno installer is the one the release page offers first: it needs
no administrator and installs into `%LOCALAPPDATA%\Programs\HylMail`. The MSI is
the one for a machine-wide or group policy deployment.

`cargo test -p hylmail-cli --test packaging` checks the templates themselves:
the version placeholders, the two binary names, the icon and licence file each
template points at, the `[package.metadata.deb]` asset list, and that the two
Windows installers use different identities. The tests run on every platform
and need no installer tooling.

## Identifiers

| Item | Value |
|---|---|
| Product name | `HylMail` |
| Workspace version | `[workspace.package] version` in the root `Cargo.toml` (single source of truth) |
| Bundle identifier | `de.hylmail.HylMail` (`hylmail_gui::BUNDLE_ID`) |
| Binary names | `hylmail-gui` (desktop) and `hylmail-cli` (terminal); `.exe` on Windows |
| Inno `AppId` | `{8E0F2C6A-3A4E-4C2B-9D62-6E6B0A1D5F31}` (fixed; identifies the per-user installation) |
| MSI `UpgradeCode` | `{0298E09C-BE9D-470C-B85F-0C857C3D0F10}` (fixed; related versions upgrade each other) |
| MSI `ProductCode` | generated by WiX (`Id="*"`), a new one per build |
| Windows ProgID | `HylMail.eml` |
| Linux desktop entry | `de.hylmail.HylMail.desktop`, icon `de.hylmail.HylMail` |
| Data directory | see the table in the top level [README](../README.md) |

The Inno `Setup` section writes the `AppId` as `AppId={{8E0F…}` - the doubled
brace escapes the one that Inno wants in the value. The preprocessor cannot
expand a `#define` there, which is why the GUID stands in the line itself.

## The two executables

`crates/hylmail-cli` builds both launchers from one library:

| Executable | Called without an argument | Used for |
|---|---|---|
| `hylmail-gui` | opens the window | the desktop entry, the installer shortcut, the `.eml` file association, the macOS bundle |
| `hylmail-cli` | prints the usage text | scripts, diagnostics, `--sync`, the terminal |

Every option exists in both; `hylmail-gui --where` and `hylmail-cli --where` are
the same program. The only difference is what an empty command line means, so
packaging always points at `hylmail-gui`.

## How a `.eml` reaches a running window

All three platforms launch the desktop executable:

```text
hylmail-gui <path>\message.eml
```

The binary acquires the single-instance lock in the configuration directory
(`ipc::acquire`). If the lock answers, this process is a *secondary*: it writes
one `OpenEml { path }` request and one `RaiseWindow` request over the loopback
endpoint and exits without creating a window. Otherwise it becomes the
*primary*, opens the window and shows the file. That is why the Windows
association, the macOS document type and the Linux `MimeType` line all point at
the executable rather than at a helper. A second start of `hylmail-cli` reaches
the same running window, because the lock lives in the configuration directory
and not in the executable.

## Icons

`icons/hylmail.svg` is the source; `cargo test -p hylmail-core --test icon_assets
-- --ignored` regenerates `hylmail-{16,24,32,48,64,128,256,512,1024}.png`,
`hylmail.ico` and `HylMail.icns` from it, using `resvg` and the `ico`/`icns`
writers that the core crate already depends on. The committed set is checked by
the non-ignored `the_committed_icon_set_is_complete` test, which also asserts
that the accent colour really covers the centre of the 256 px tile.

The two container formats have opposite byte orders - `.ico` is little endian,
`.icns` is big endian - so the writers are separate functions.

The Windows executables themselves carry no icon resource; Explorer and the
Start menu take the icon from `hylmail.ico` through `SetupIconFile`,
`DefaultIcon` and `IconFilename`. The icon of the *running* window comes from
the toolkit and is the same 256 px PNG.

## Windows

### Inno Setup (per user)

`windows/hylmail.iss` installs `hylmail-gui.exe` and `hylmail-cli.exe` into
`%LOCALAPPDATA%\Programs\HylMail`, registers `HylMail.eml` so a double click on a
message opens it in a running instance, and creates a start menu group with
`HylMail`, `HylMail (Befehlszeile)` and an optional desktop shortcut. Uninstall
leaves `%APPDATA%\HylMail` and `%LOCALAPPDATA%\HylMail` alone and asks before
deleting them.

```powershell
cargo build --release -p hylmail-cli
iscc /DHylMailVersion=0.1.0 packaging\windows\hylmail.iss
```

The compiler writes `dist\HylMail-<version>-setup.exe`. The script needs Inno
Setup 6.1 or newer; it was compiled with 6.7.4, which is what the release
workflow installs. Inno Setup 7 is not used: its installer refuses to run under
Wine, so the script could not be checked here.

### WiX MSI (per machine)

`windows/hylmail.wxs` builds a per-machine MSI that installs into
`Program Files\HylMail`, creates an all-users start menu entry and the same
`HylMail.eml` association, and appears under *Apps & features* with the icon,
the version and the project link. It has no `UIRef`, so it runs with the plain
Windows progress dialog and needs no `WixUIExtension` or RTF licence page.

```powershell
cargo build --release -p hylmail-cli
candle.exe -nologo -dHylMailVersion=0.1.0 -out dist\hylmail.wixobj packaging\windows\hylmail.wxs
light.exe  -nologo -sice:ICE61 -out dist\HylMail-0.1.0.msi dist\hylmail.wixobj
```

`MajorUpgrade` compares the first three parts of the version and is set to
`AllowSameVersionUpgrades="yes"`, so a rebuilt 0.1.0 replaces an installed
0.1.0 - which is what makes re-running the release idempotent. That attribute
normally earns the `ICE61` validation warning, hence the documented
`-sice:ICE61` suppression. The version must stay numeric: MSI has no place for
a `-rc1` suffix, so a prerelease tag has to bump the number.

The window is created with the `glow` renderer, which needs a working OpenGL
1.4 driver; on a machine without one, Windows falls back to the software GL
implementation shipped since Windows 10.

## macOS

`macos/make-app.sh [VERSION] [BIN_DIR]` assembles `dist/HylMail.app` by hand:

* `Contents/MacOS/hylmail-gui` and `Contents/MacOS/hylmail-cli`,
* `Contents/Info.plist` from `macos/Info.plist` with `{{VERSION}}` replaced,
* `Contents/Resources/HylMail.icns` plus the licence file,
* `Contents/PkgInfo` with `APPL????`.

The script asserts that the rendered `CFBundleIdentifier` is
`de.hylmail.HylMail`, so a drift from `hylmail_gui::BUNDLE_ID` fails the build.
With `HYLMAIL_SIGN_IDENTITY` set it runs
`codesign --force --deep --sign "$HYLMAIL_SIGN_IDENTITY"`, so the local builds
stay unsigned.

`macos/make-dmg.sh [VERSION]` stages the bundle next to an `/Applications`
symlink and calls `hdiutil create -format UDZO`. It refuses to run anywhere
without `hdiutil`, and `HYLMAIL_SKIP_APP=1` reuses an existing `HylMail.app`.

The release workflow builds both `aarch64-apple-darwin` and
`x86_64-apple-darwin` and combines the two launchers with `lipo -create` into a
universal binary before the bundle is assembled. `LSMinimumSystemVersion` is
`11.0`, the earliest release with a Metal-capable OpenGL layer that `glow` is
happy with. Notarisation is not wired up yet.

## Linux

`cargo deb -p hylmail-cli --no-build` builds `hylmail_<version>-1_amd64.deb` from
the asset list in `crates/hylmail-cli/Cargo.toml`: both binaries into
`/usr/bin`, the desktop entry into `/usr/share/applications`, the 16 to 512 px
icons into `/usr/share/icons/hicolor`, the README and the copyright file into
`/usr/share/doc/hylmail`. The four libraries that `winit` opens through `dlopen`
- X11, Wayland, xkbcommon and OpenGL - are named by hand, because `$auto` only
sees the libraries that end up in the ELF headers.

`linux/make-tarball.sh [VERSION] [BIN_DIR]` stages the same file list under
`HylMail-<version>/` and writes `dist/HylMail-<version>-<target-triple>.tar.gz`
(`.deb` is produced on x86_64 only).

`StartupWMClass` matches the `with_app_id` value the window sets, so a window
that was started from the menu is still recognised as HylMail by the shell. The
desktop entry deliberately does not claim `x-scheme-handler/mailto`: HylMail
does not open a `mailto:` URL, and advertising it would put the application in
the list of mail handlers on every desktop.

## The release workflow

`.github/workflows/release.yml` runs on a `v*` tag (and on manual dispatch):

1. `version` reads the version out of `cargo metadata` and fails if the tag
   does not match it,
2. `windows` builds the workspace and runs Inno Setup 6.7.4 and WiX 3.14.1 -
   both downloaded from their pinned releases in this job, so the CI uses the
   versions the templates were checked with,
3. `macos` builds both architectures, `lipo`s them together and runs the two
   scripts, then verifies the image with `hdiutil verify` and a read-only
   attach,
4. `linux` builds the launchers, runs `cargo deb` and the tarball script, and
   inspects both archives (`dpkg-deb -I/-c`, `tar -tzf`) before they are
   uploaded,
5. `release` collects every artifact and attaches them to the GitHub release.

Every upload step uses `if-no-files-found: error`, and the Windows job throws
if an installer comes out smaller than 5 MB, so a silently skipped package
cannot end up in a release.

## Verification

Checked here, on a Linux and a Windows machine:

* the MSI was built with WiX 3.14.1 and its tables inspected (`msiinfo`): the
  file, registry, shortcut and feature tables match the source,
* `hylmail.iss` was compiled with Inno Setup 6.7.4 under Wine; the compiler
  reported no warning and packed all five files,
* the `.deb` was built with `cargo-deb` and inspected with `dpkg-deb`,
* both macOS scripts were run; `make-dmg.sh` refuses on Linux as intended,
* the icon set and every template invariant is covered by
  `cargo test --workspace`.

Only the release CI can check what needs macOS or a real Windows installation:
the `.dmg`, the signing identity, and the two installers' uninstall behaviour.
